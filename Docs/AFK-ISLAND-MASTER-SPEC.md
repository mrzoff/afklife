# ЧАСТЬ I. ВИДЕНИЕ ПРОЕКТА

## 1. Концепция AFK ISLAND

AFK ISLAND — мобильная игра в жанре Idle / AFK Simulator / Cozy Island Builder.

Игрок получает небольшой необитаемый остров и постепенно превращает его в живую экосистему.

Основная особенность игры — остров продолжает развиваться, даже когда приложение закрыто.

На острове самостоятельно:

- растут растения;
- расширяется суша;
- появляются новые участки растительности;
- заселяются животные;
- меняется экосистема;
- происходят природные события;
- меняются погодные условия;
- развивается поселение;
- накапливаются результаты, которые игрок обнаруживает при возвращении.

Игрок может наблюдать за миром, влиять на его развитие, заниматься коллекционированием, участвовать в мини-играх и постепенно открывать новые возможности.

## 2. Главный игровой принцип

**Игрок не должен чувствовать обязанность постоянно заходить в игру.**

Отсутствие игрока не должно приводить к:

- гибели растений;
- потере прогресса;
- разрушению поселения;
- уничтожению накопленных результатов;
- обязательному ежедневному входу;
- искусственному ограничению прогресса 24 часами.

Чем дольше игрок отсутствует, тем больше изменений он может обнаружить после возвращения.

Офлайн-развитие — основа игры, а активная игра дополняет его.

## 3. Основной игровой цикл

1. Игрок открывает игру.
2. Получает отчёт о событиях за время отсутствия.
3. Осматривает изменившийся остров.
4. Изучает новые растения, животных и природные явления.
5. При необходимости участвует в активностях.
6. Развивает остров и открывает новые возможности.
7. Закрывает приложение.
8. Мир продолжает развиваться автоматически.

Ориентиры распределения ценности из GDD:

| Источник | Целевой вклад |
|---|---:|
| Офлайн-развитие | 75% |
| Активная игра и мини-игры | 15% |
| События и задания | 10% |

Это ориентир для балансировки, а не жёсткое требование.

## 5. Общая архитектура

Игровые системы должны быть разделены по назначению.

### 5.1. Data

Отвечает за:

- сериализуемые модели;
- состояние игрового мира;
- постоянные ID;
- конфигурацию;
- каталоги объектов;
- ScriptableObjects.

### 5.2. Simulation

Отвечает за:

- расчёт роста;
- расширение мира;
- развитие экосистемы;
- появление животных;
- природные события;
- погоду;
- развитие поселения;
- офлайн-результаты.

Simulation не должна зависеть от GameObject, камеры или UI, если это не требуется конкретным визуальным процессом.

### 5.3. Runtime Controllers

Отвечают за:

- пользовательский ввод;
- запуск активностей;
- переходы состояний;
- вызов Simulation;
- передачу результатов в UI.

### 5.4. Visualizers

Отвечают за отображение уже рассчитанного состояния.

Визуализаторы не должны самостоятельно изменять авторитетные игровые данные.

### 5.5. UI

Отображает данные и принимает действия пользователя.

UI не должен самостоятельно рассчитывать игровой прогресс или напрямую изменять сохранение в обход соответствующих сервисов.

# ЧАСТЬ III. СОХРАНЕНИЕ И ОФЛАЙН-СИМУЛЯЦИЯ

## 6. Save Architecture

**Существующая система сохранений является фундаментом проекта.**

Основные компоненты:

- GameSaveData;
- SaveService;
- SaveMigrationService;
- SaveClone;
- GameBootstrap.

Текущая известная версия сохранения: **Save v8**.

Отдельный SaveManager не создавать: сохранение реализовано через SaveService.

### 6.1. Обязательные правила

- Постоянные ID игровых объектов.
- Совместимые миграции старых сохранений.
- Сохранение координат и состояния объектов.
- Отдельный watermark для симуляции мира.
- Отсутствие повторного начисления офлайн-прогресса.
- Защита от повреждения файлов.
- Наличие резервной копии.
- Запрет перезаписи сохранения более новой неподдерживаемой версии.
- Безопасная обработка ошибок записи.

### 6.2. Транзакционный принцип

Для общей офлайн-симуляции:

`Read → Migrate → Clone → Simulate → Validate → Write → Commit → Restore Visuals → Report`

Если запись не удалась:

- не продвигать watermark;
- не считать симуляцию применённой;
- не терять исходное сохранение;
- разрешать повторную обработку периода.

### 6.3. Запреты

Без отдельного контракта запрещено:

- менять SaveService;
- менять схему резервирования;
- менять механизм блокировки новой версии;
- повышать Save version;
- менять миграции;
- менять формат ID.

Любая новая система, сохраняющая состояние, должна получить собственные сериализуемые модели и миграционный контракт.

## 8. GDD 0.2 — Living Island / World Growth

<badge color="success">Основная реализация принята</badge>

### Цель

Перейти от небольшого статичного острова к бесконечно расширяемому логическому миру.

### Принятые решения

- Один остров продолжает расширяться.
- Нет системы отдельных уровней-карт.
- Расширение происходит органически.
- Край острова неровный.
- Рост не должен выглядеть шахматной сеткой.
- Скорость расширения уменьшается по мере увеличения площади.
- Chunk — техническая единица сохранения, а не видимый квадрат.

### Техническая структура

- Chunk: 16×16.
- Координаты: chunkX + chunkZ.
- Логическое состояние отделено от загруженных GameObject.
- Клеточная маска хранит стадии развития земли.
- Визуальная геометрия формируется отдельно.
- Офлайн-расширение рассчитывается математически и временными интервалами.

### Основные системы

- WorldGrowthSimulation;
- WorldGrowthService;
- ChunkManager;
- IslandChunk;
- SaveMigrationService;
- OfflineGrowthService;
- IslandMeshVisualizer.

### Дополнительные системы

- природная колонизация;
- растительность на новых участках;
- фауна;
- погодные условия;
- события;
- поселение на выросшей земле.

### Важное ограничение

Существующие растения, их ID и координаты нельзя терять или перемещать при миграциях и расширении мира.

### Статус

Логическое расширение мира и Living Offline приняты.

Дальнейшие изменения должны сохранять текущую архитектуру.

- материалы растительности;
- alpha clipping;
- нормали;
- поведение деформации;
- совместимость с LOD.

Предварительное заключение: шейдер ветра не является доказанной причиной плохого качества деревьев при zoom-out.

Переписывать его без установленной причины запрещено.

### 20.5. 11E-5 — Camera Visual QA

Проверить:

- минимальный zoom;
- средний zoom;
- максимальный zoom;
- Pan;
- диагональное перемещение;
- zoom вместе с перемещением;
- длительное движение по карте;
- отсутствие отрыва объектов от земли;
- корректность hit testing.

### 20.6. Отдельная проверка водоёма

В рамках общей стабилизации мира необходимо проверить:

- WaterSource;
- PondHitProxy;
- взаимодействие с деревьями;
- взаимодействие с поселением;
- перекрытие raycast;
- защиту водоёма от заселения деревьями;
- корректность отображения водной поверхности.

Нельзя допускать, чтобы деревья закрывали водоём или чтобы попадание по посторонним объектам запускало рыбалку.

Ввести единое правило резервирования водной области только после аудита существующих алгоритмов колонизации и визуализации.

1. Изучить текущий проект.
2. Проверить актуальную структуру файлов.
3. Проверить связанные системы.
4. Изучить существующие Smoke.
5. Проверить Save и миграции, если этап их затрагивает.
6. Определить минимальный набор изменений.
7. Составить технический план.
8. Не менять несвязанные системы.

## 40. Формат каждого этапа

Каждый этап обязан содержать:

### A. Audit

Что существует в проекте на самом деле.

### B. Scope

Что входит и что запрещено менять.

### C. Architecture

Какие компоненты отвечают за данные, симуляцию, контроллеры и визуализацию.

### D. Implementation

Точные изменения по файлам.

### E. Smoke

Автоматические и Editor-проверки.

### F. Regression

Проверка существующих систем.

### G. Build

Сборка, версия и versionCode, если выполнялась.

### H. Device Test

Проверка на BlueStacks или физическом устройстве.

### I. Final Report

Фактический результат и оставшиеся проблемы.

## 41. Статусы

Использовать только следующие статусы:

- `AUDIT COMPLETE`
- `READY FOR IMPLEMENTATION`
- `IN PROGRESS`
- `CODE PASS`
- `SMOKE PASS`
- `BUILD PASS`
- `DEVICE PASS`
- `ACCEPTED`
- `NEEDS REVIEW`
- `BLOCKED`

Нельзя объявлять этап завершённым только потому, что код написан.

## 42. Обязательные правила сохранения

Каждый этап, затрагивающий Save, должен проверять:

- загрузку старого сохранения;
- миграцию;
- отсутствие потери данных;
- повторную загрузку;
- резервную копию;
- защиту от новой неподдерживаемой версии;
- отсутствие повторного начисления;
- сохранение после force-stop.

## 43. Обязательные правила офлайн-систем

- Никакой обязательной работы приложения в фоне.
- Не рассчитывать каждую секунду отсутствия.
- Использовать математические расчёты и ограниченные временные шаги.
- Использовать отдельные watermark.
- Не начислять один период дважды.
- Не терять прогресс при ошибке.
- Не наказывать игрока за отсутствие.
- Не создавать визуальные объекты внутри чистой Simulation.

## 44. Правила работы с ассетами

- Не импортировать большие наборы без необходимости.
- Не заменять рабочие модели без визуального сравнения.
- Проверять лицензию каждого стороннего ассета.
- Проверять совместимость с Unity 6 URP.
- Следить за единым масштабом и стилем.
- Проверять LOD и материалы.
- Проверять мобильную производительность.

## 45. Правила изменения существующих систем

Системы, которые уже приняты, не переписывать только ради нового этапа.

Если необходимо изменить существующую систему:

1. Провести аудит.
2. Зафиксировать текущий контракт.
3. Определить конкретную причину.
4. Подготовить отдельный diff.
5. Проверить старые сценарии.
6. Проверить сохранение.
7. Проверить работу после restart.

- новые территории появляются органически;

- длительное отсутствие не ломает мир;

- растительность качественно отображается на всех дистанциях;

- производительность соответствует целевому профилю;
- сохранение совместимо между обновлениями;
- отсутствуют критические ошибки.

# 48. ГЛАВНОЕ ПРАВИЛО ПРОЕКТА

AFK ISLAND — не набор независимых мини-игр и систем.

Это один постоянно развивающийся живой мир.

Каждая новая функция должна усиливать эту концепцию.

Нельзя добавлять систему только потому, что она привычна для idle-игр.

Любая новая механика должна отвечать хотя бы на один вопрос:

- Как она влияет на живой остров?
- Что происходит с ней во время отсутствия игрока?
- Как она делает возвращение интереснее?
- Как она расширяет экосистему или коллекцию?
- Как она помогает игроку взаимодействовать с миром?

Если система не усиливает основную концепцию, её необходимость должна быть отдельно обоснована.

**Финальная цель: создать красивый, самостоятельный, бесконечно развивающийся остров, на который игроку хочется возвращаться не из-за обязательств, а из-за любопытства увидеть, что произошло за время его отсутствия.**
